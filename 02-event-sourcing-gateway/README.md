# 02 · Транзакционный шлюз на событийном журнале

**Файл:** [`Gateway.gs`](Gateway.gs)

## Задача

Данные проекта вносят параллельно семь ролей — разные отделы, разные этапы, разные поля.
При обычной работе «пишем значение в ячейку» через месяц невозможно ответить
на простые вопросы: кто поставил эту цифру, что было до неё, когда её перекрыли.
А при одновременной работе двух человек часть правок просто теряется.

## Решение

**Event sourcing.** Данные не перезаписываются никогда:

```
запись пользователя  →  строка в append-only журнале tx_journal
                                    ↓  пересборка
текущее состояние    →  витрина view_current_state
                        (последняя запись на ключ projectId|wbsCode|parameterCode)
```

Журнал — источник истины, витрина — производная, её можно снести и пересобрать.
Витрина хранит в том числе автора последней правки, поэтому дашборд показывает «кто внёс».

## Что смотреть в коде

| Функция | Что делает |
|---|---|
| `processTransaction` | Шлюз целиком: валидация → авторизация → права → дедуп → атомарная запись |
| `rebuildCurrentViews` | Пересборка витрины из журнала: последняя запись на ключ |
| `isDuplicate` / `rowHash` | Идемпотентность по `txId` и контроль целостности строки |
| `_readSheetCached` | Кэш справочников в `CacheService` с TTL и явной инвалидацией |
| `logRequest` / `logError` | Наблюдаемость: каждый запрос с длительностью в мс и статусом |

Порядок проверок в `processTransaction` не случайный: сначала дешёвая структурная
проверка пакета, затем авторизация, затем права роли, и только потом — дорогая
построчная валидация. Отказ происходит на самом дешёвом шаге, до взятия блокировки.

## Ключевые решения и почему так

**Роль с клиента игнорируется.** Клиент присылает роль, сервер её не использует —
роль берётся из справочника `sys_users` по email. Иначе достаточно подменить запрос.

**Дедуп и запись под единой блокировкой.** Если проверять дубль до блокировки,
два одновременных запроса с одним `txId` оба пройдут проверку и запишут дубль.
`LockService` закрывает это окно.

**Кэшируются только медленные данные.** Справочники (роли, права, параметры) меняются
редко → в кэш на 5 минут. Живые данные — журнал, витрина, проекты — читаются напрямую:
показать устаревшие данные хуже, чем потратить 200 мс.

## Что обычно спрашивают

**Не растёт ли журнал бесконечно?**
Растёт — это плата за историю. Пересборка витрины читает журнал целиком, поэтому
при дальнейшем росте следующий шаг — инкрементальная пересборка или перенос
журнала в полноценную СУБД. Для текущих объёмов предприятия запас есть.

**Зачем хэш строки, если есть `txId`?**
`txId` защищает от повтора всей транзакции, хэш строки — контроль целостности
конкретного значения: видно, что строка в журнале не правилась руками задним числом.
