# 03 · Ролевая модель на уровне отдельных полей

**Файл:** [`RoleModel.gs`](RoleModel.gs)

## Задача

Обычная ролевая модель раздаёт права «на экран»: этой роли доступен такой-то раздел.
Здесь так не работает. Одну форму этапа заполняют несколько отделов, и **ответственность
разделена по конкретным параметрам**: сметчик отвечает за свои строки, снабжение —
за свои, ПТО — за свои, и всё это в одной таблице одного этапа.

Нужны права не на экран, а на поле.

## Решение

Матрица «роль × параметр» вынесена в справочник `sys_role_fields` — она была собрана
из реальных колонок «ответственный» в рабочем справочнике параметров, то есть модель
доступа повторяет уже сложившееся в компании распределение ответственности.

Права нигде не зашиты в код. Управление — четыре справочных листа:

| Лист | Отвечает за |
|---|---|
| `sys_users` | кто активен и с какой ролью |
| `sys_permissions` | какая роль в какой АРМ может писать |
| `sys_role_fields` | **матрица «роль × параметр»** |
| `sys_parameters` | реестр параметров: тип значения, домен |

Добавить роль или передать поле другому отделу = дописать строки в таблицу.
**Без правки кода и без редеплоя.**

## Два барьера

```
1. Видимость   getStageForm → _roleAllowedCodes → роль получает только свои поля
2. Запись      validateRows → та же матрица, проверка уже на сервере
```

Второй барьер — не дублирование, а единственная настоящая защита. Скрыть поле в UI
нельзя считать безопасностью: клиент можно подменить и отправить запрос напрямую.
Поэтому сервер проверяет матрицу заново, независимо от того, что показала форма.

## Что смотреть в коде

| Функция | Что делает |
|---|---|
| `_roleAllowedCodes` | Множество разрешённых роли параметров. `ROLE_ADMIN` → `null` (wildcard, без фильтра) |
| `validateRows` | Серверный барьер: регистрация параметра, домен, field-level право, тип значения |
| `canWrite` | Право роли писать в данный АРМ (грубый барьер поверх тонкого) |
| `getActiveUser` | Единственный источник роли — справочник, не клиент |
| `_requireUser` | Страховка для серверных функций на случай вызова в обход рендера страницы |

## Ключевое решение: «роль без строк видит ноль полей»

`_roleAllowedCodes` для роли без записей возвращает пустой словарь, а не «разрешить всё».
Это осознанный выбор в пользу **fail-closed**: опечатка в названии роли или забытая
настройка приводит к тому, что человек не видит ничего и приходит с вопросом —
а не к тому, что он молча получает доступ ко всем полям.

## Что обычно спрашивают

**Почему права в таблице, а не в коде?**
Меняются не реже, чем идёт работа: перераспределили ответственность — поменяли строку.
Если бы это жило в коде, каждое кадровое изменение требовало бы правки и редеплоя,
то есть меня. Сейчас это делает администратор контура.

**Чем плох `ROLE_ADMIN` как wildcard?**
Тем, что это исключение из общего правила, и его нужно держать в голове при отладке.
Осознанный компромисс: альтернатива — прописывать админу все 164 параметра строками
и поддерживать этот список при каждом добавлении параметра.
